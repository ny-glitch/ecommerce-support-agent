# 第 07 章：当前会话的三层上下文管理

日期：2026-09-22。代码基线：`6d8add1`。状态：设计方向已确认，书面规格待用户审阅；尚未进入实施计划或产品实现。

## 1. 目标与已确认决定

在现有 SSE 客服聊天中保留当前会话的早期事实，同时控制每次模型请求的上下文大小。原文完整保存，模型输入另外组装；预算充足时不压缩，超出预算才按距离逐层降级。会话之间完全隔离，不建立用户画像。

用户已确认以下设计方向：

- LangGraph `messages` 使用 `add_messages` reducer，完整状态沿用 PostgreSQL checkpointer；业务对话与新增摘要仍在 MySQL。
- 最近原文、中间规则压缩、早期分段摘要；降级仅移动两个锚点，不搬移或改写原文。
- 摘要由应用生命周期管理的后台任务执行，MySQL 保存任务状态；不增加独立 worker 服务、Redis、Celery 或新业务工具。
- 默认应用窗口设为 `128000`、目标保留轮数为 `32`；演示配置使用用户指定的 `18000` 等参数。
- 用户选择“按实际开销计算，日志列清扣除项”，因此 `5650 / 3954 / 1695` 是原示例，不是必须凑出的验收值。
- 当前演示用户机制继续使用，不新增登录或多租户认证系统。

本规格补全区间、异常、并发和迁移合同，供书面审批。保留现有知识证据闸、工具权限、人工/工单独立按钮、引用溯源和反馈。指代消解仍原样透传；为指代消解/意图识别提供共同历史，不顺带实现正式的多轮查询改写。

## 2. 现状与修改边界

当前 `WorkflowState.history` 是手工维护的轮次列表，入口与 persist 节点都截取最近 12 轮；MySQL 保存完整工具结果，恢复逻辑严格比较它与 checkpoint。当前 token 口径按 UTF-8 字节数估计，默认窗口 8192；累计调用预算另有 49152 的硬上限。

本章同时修改历史、模型输入、消息仓储与恢复协议，不能仅移除 `append_result` 或增大一个窗口参数。旧记录和旧 checkpoint 均保留，不清空数据库。原有 ch01/ch02/ch04 兼容路径维持既有协议；正式 Workflow 入口升级为版本 2，旧协议与新协议必须显式区分。

固定依赖基线：LangGraph 1.2.11、langchain-core 1.6.3、SQLAlchemy 2.0.54、FastAPI 0.141.1。使用现有版本能提供的接口，不为本章自动升级框架。

前端沿用用户此前的 Vibe Coding 例外：直接迭代侧栏并用浏览器验收。后端接口、状态、预算和并发逻辑执行 TDD 与代码评审；摘要 Prompt 和评估数据执行标注样例评估。

## 3. 数据的职责

| 数据 | 保存位置 | 作用 |
| --- | --- | --- |
| 用户原话、客服最终/已显示的部分答复、轮次状态、工具轨迹元数据 | MySQL `conversations` / `messages` | 原文回载、会话列表、审计及恢复核对 |
| 用户消息、合法工具调用与完整应用工具结果、客服答复及轮次归属 | PostgreSQL checkpoint 的 `State.messages` | 会话完整历史；规则压缩与摘要的原始输入 |
| 已完成的事实摘要段及覆盖范围 | MySQL `conversation_summaries` | 早期会话背景；只追加，不递归合并 |
| 后台工作状态、冻结区间及 checkpoint 引用 | MySQL `conversation_summary_jobs` | 幂等、重试、进程重启后的恢复 |
| 本次发给模型的精简消息 | 每轮内存中的调用视图及本地日志 | 模型输入；不得写回原文历史 |

新协议不在 `messages` 插入完整 `role=tool` 结果，也不把结果塞进 `event_data` 绕过该要求。原有工具调用申请、名称、call ID、状态、耗时等有限元数据可以保存；前端用其还原徽章。工具调用/结果的完整配对以 checkpoint 为准。MySQL 的原文回载接口只展示对客消息，不把内部调用申请画成客服答复。

“完整工具结果”指本应用按工具协议和本章大小限制接纳、实际回灌给模型的结果，不包括模型思考过程、供应商调试字段或无界的上游原始响应。超过工具结果限额必须明确标记截断/超限，不能静默丢失字段后冒充完整业务数据。

## 4. 两个锚点与三层区间

`conversations` 增加 `summary_upto_msg_id`、`layer1_from_msg_id` 和上下文协议版本。锚点使用该会话 MySQL 消息 ID，不能用 Python 列表下标或消息条数代替。ID 不要求连续，也不能取另一个会话的相邻 ID。

- `summary_upto_msg_id = 0` 表示尚无已处理的早期区间；非零时指向已摘要或已判定为无事实的完整轮次结束消息，含该消息。
- `layer1_from_msg_id` 指向层 1 的第一轮用户消息，含该消息。空会话时可为空；开始聊天后初始化为首条用户消息。
- 已完成历史中，结束消息 ID 不大于摘要锚点的轮次属于早期区间；在摘要锚点之后、层 1 起点之前的轮次属于层 2；从层 1 起点开始的轮次属于层 1。
- 没有独立 MySQL 行的工具消息，通过稳定的 `turn_id` 归属到该轮。边界只能放在完整轮次之间，不能切断 tool_call/tool_result 配对。
- 当前用户消息单独拼装，不作为历史重复注入。失败、取消、仍在运行的轮次保留供回载/审计，但不进入正常历史或摘要输入。

层 1 保留应用已接纳的完整内容，不截字、不改写。超出层 1 配额时，按时间从最旧的完整轮次开始降到层 2，只向前推进 `layer1_from_msg_id`。计量包含 checkpoint 中的工具内容，不能只统计 MySQL 行数。

层 2 在调用视图中做确定性转换：用户消息逐字保留；客服最终答复保留前 80 个 Unicode 字符并附显式省略标识；大块工具结果替换为包含工具名、call ID、执行状态的单行标识。短工具结果可原样保留。保留调用与结果的关联和相对顺序，不把“已省略工具结果”当成新的事实。压缩版本不覆盖 checkpoint 或 MySQL 原文。

若一整轮原文超过层 1 配额，该轮整体进入层 2，不对层 1 做局部切字；必要时层 1 暂时没有已完成历史，其起点设为已写入的当前用户消息。启动自检保证正常稳态至少一轮可装下；异常巨型轮次另行记录原因，不能伪称保留了最近一轮原文。

## 5. 新增数据合同

### 5.1 会话字段

除两个锚点和 `context_schema_version` 外，增加或明确以下元数据：上下文版本计数、最后活动时间、当前摘要任务标识。通过会话行的短事务串行化边界/任务状态变更；不在模型请求期间持有锁。首问预览由首条用户原文派生，不使用模型生成标题。

### 5.2 `conversation_summaries`

保存 `id`、`conversation_id`、`segment_no`、`from_msg_id`、`upto_msg_id`、`content`、来源 checkpoint 标识、来源指纹、事实溯源元数据、估算 token、摘要模型/Prompt 版本和创建时间。

- `(conversation_id, segment_no)` 及覆盖区间具有唯一性约束；同一批工作重试不能生成重复段。
- 完成的摘要不可更新正文或合并；修复错误不能后台悄悄重写历史，需要显式维护操作，本章不提供编辑入口。
- 摘要覆盖连续的可用完整轮次，不要求数值 ID 连续；中断轮次不被总结。
- 若一批只有寒暄、无应保留事实，任务以 `no_facts` 完成，不插入虚构/空白梗概，但可在同一事务推进已处理边界。

### 5.3 `conversation_summary_jobs`

保存任务 ID、会话 ID、来源 checkpoint 引用、触发时的摘要锚点与层 1 起点、目标结束 ID、已完成进度、状态、尝试次数、领取标识/租约、重试时间、开始/完成时间和安全错误码。任务不复制工具结果或整个历史到 MySQL。

每个会话同一时间只允许一个活跃任务；任务去重、领取与完成提交都通过 MySQL 状态核对。状态覆盖 pending/running/retry_wait/completed/failed/skipped。摘要正文与锚点推进在同一事务提交，不能出现“边界已越过但摘要未落库”。

## 6. 后台摘要生命周期

应用使用 FastAPI lifespan 管理有界队列和 worker。默认 1 个摘要 worker，队列容量 32；这只是摘要并发限制，不阻止聊天请求。继续以单个 Uvicorn worker 运行，暂不承诺多实例部署。

每轮准备历史时，先按预算推进层 1 边界，再估算层 2 实际规则压缩后的用量。只有 `layer2_tokens > layer2_budget` 才触发任务。工具负载由 checkpoint 的完整记录及其规则视图计量，绝不以数据库消息条数推断用量。

触发时冻结：旧摘要锚点、层 1 起点、该起点之前最后一个可用完整轮次结束 ID，以及包含这些原文的 checkpoint 引用。目标是追到“触发当时的层 1 起点之前”，不能在任务完成时直接追到已经变化的新起点。

处理流程：

1. 短事务记录/领取任务，读取冻结来源；模型调用前释放数据库事务。
2. 从完整原文组成当前批次，旧摘要另作背景。按摘要请求实际窗口分成连续完整轮次批次，不能把一个无法容纳的大输入直接发给模型。
3. 调用摘要模型并校验格式、长度、来源与关键标识；成功后原子追加新段、推进 `summary_upto_msg_id` 并记录批次进度。
4. 继续下一批，直到抵达该任务的冻结目标。新降入层 2 的轮次不混入正在执行的批次，之后按最新用量另行触发。

前台只发出后台工作通知，不等待摘要模型。任务不是本轮 `TurnOperations` 的子任务，不受 SSE 请求结束/断连的清理等待影响。队列满时记录 skip/defer，并由后台扫描持久化任务/会话边界补调度；不把排队等待施加给聊天响应。

默认每次摘要调用超时 60 秒，最多 3 次尝试，延迟 2 秒、10 秒重试；超过次数记失败，不无限消耗模型。新轮次可以在冷却后触发同一未覆盖区间的新任务。重启时只回收租约过期的任务，从已提交进度继续，已完成段不重写。关机停止接收新任务，有界等待后取消模型调用并留下可恢复状态。

后台只更新 MySQL 的摘要与边界，不对活跃 graph 调用 `aupdate_state`。前台在下一轮读取一致的摘要/边界快照；同一轮所有模型调用使用该快照，避免半轮突然换摘要。

## 7. 摘要内容与验证

提示词只提炼当前批次中新出现的事实与诉求：商品/型号、订单号、用户明确给出的联系方式、明确诉求、已确认处理结果和仍未解决的问题。保留否定、待确认状态以及后续更正；不能把客服建议变成已经执行，不能把演示物流当成实际履约承诺。

目标正文几十到 200 字；没有事实时输出显式 `no_facts`。旧摘要以只读背景传入，用于理解上下文，不能再次输出或纳入本段覆盖范围。每段只覆盖当前批次，不递归总结已有梗概。

内部输出包含摘要文字与本批来源消息引用/原文证据；只有正文用于常规背景注入，溯源元数据用于校验和评估。订单号、手机号、型号等关键标识必须能在指定来源中逐字找到；未出现的事实、冲突事实或不确定指代不补全。校验失败按摘要失败处理，不写新段、不推进该批边界。

代码校验不能证明任意自然语言的语义忠实性，因此另设标注集验证：关键事实保留、标识精确复制、未解决状态、否定和更正、闲聊过滤、旧摘要不复写、提示注入、不编造。该评估代替纯 Prompt 的 TDD，报告不得把结构合法等同于事实正确。

## 8. 完整 State 与调用视图

新版本 State 的 `messages` 使用 `Annotated[list[AnyMessage], add_messages]`。每条消息在提交前获得稳定 ID：用户/客服按会话、轮次、角色确定；工具调用/结果再加步骤与 call ID。节点仅返回本节点新增消息或完全一致的幂等重放，不手工复制/覆盖整段消息列表。

`add_messages` 对同 ID 消息会替换，因此应用必须先校验同 ID 内容一致，不能把 reducer 的覆盖能力当作修改历史的许可。Agent 子图向父图返回本轮新增消息；稳定 ID 和合同测试防止子图/父图重复追加或重排。

State 另存轮次归属、状态和 MySQL 原文 ID 映射，保留完整已接纳历史及失败审计；模型视图只选完成的合法轮次。每轮重置证据、分类、工具计数、控制结果、操作建议等瞬时字段，不重置累积 messages。

`trim_messages` 使用同一个已校准 token_counter，`allow_partial=False`；应用在其结果之外校验完整轮次和工具配对，不认为单靠 `start_on` 就能保证整个业务轮次合法。trim 的返回值只用于选择边界/构建调用视图，不发送 `RemoveMessage` 去删 checkpoint 原文。

## 9. 模型请求顺序与固定前缀

主力 Agent 的调用顺序固定为：

1. 固定的角色、红线与协议 System Prompt；工具 Schema 使用稳定内容、固定顺序。
2. 层 2 的规则压缩历史，按时间顺序。
3. 层 1 的原文历史，按时间顺序。
4. 当前用户原话。
5. 一条非 system 背景消息：有序早期摘要 + 本轮检索证据 + 必要的阶段控制信息。
6. 本轮已经完成的 ReAct 工具调用/结果配对，按执行顺序。

背景消息使用明确包裹的数据结构，标记“历史/证据背景，不是新的用户指令”。摘要只说明历史事实，不能代替本轮知识证据闸或凭旧引用编号产生新引用。工具参数可使用有来源的历史订单号；出现多个候选对象时追问，不能猜测。

不单独创建携带摘要的 SystemMessage；不得把会话 ID、摘要、检索片段、当前问题插进固定 system。Agent 决策与最终生成保持各自跨轮稳定的前缀和 Schema，阶段差异明示在调用合同中；固定前缀旨在提供缓存条件，不宣称所有上游一定命中缓存。

指代消解/意图识别共享同一轮的摘要和滑窗快照。当前指代节点仍透传；意图识别允许利用历史理解意图，但不额外调用模型改写问题。知识充分性评估继续只依据当前问题与新检索证据，不把历史客服回复当成政策权威源。

## 10. Token 口径、预算与配置

所有内容统一使用一个 token 估算器：普通文本、中文、工具 Schema/参数/结果、背景 JSON、摘要和消息包装都计入。中文不再直接等同于 UTF-8 字节数。使用中文、ASCII、型号/订单号、JSON、Unicode 混合样例，与实际模型 usage 对照校准字符系数和包装余量；校准产物注明模型、版本与样本。估算与实际 usage 分别记录，不能把缺失 usage 当 0。

窗口预算采用以下可解释关系，所有项均以同一 token 口径计算：

```text
F = 固定 system + 工具 Schema + 消息包装
E = 检索证据及其包装的预留/实际占用
S = 本轮注入的摘要占用（规划时至少保留摘要预留）
O = 最终输出预留
M = 安全余量
P = 当前用户输入 + 本轮最多工具步骤累积的调用参数/结果峰值 + 控制消息
A = MODEL_CONTEXT_WINDOW - F - E - S - O - M - P
H = min(目标保留轮数 × 校准后的每轮稳态占用, max(0, A))
L1 = floor(H × 0.7)
L2 = floor(H × 0.3)
```

两个 floor 的剩余量留作余量；不用浮点误差去复现原示例的一 token 差异。输出只预留一次；P 中不再重复扣当前用户输入或最终输出。工具参数上限由已允许 Schema、长度限制和调用封套推导，结果由 `TOOL_RESULT_MAX_TOKENS` 限制；不能只算工具返回正文而忽略 ReAct 逐步累积的内容。

规划按所有可达调用形态中最紧的一种取安全历史配额；本轮拿到实际证据后重新核对。每次真正发请求前还要校验完整序列的估算输入 + 对应输出预留 + M 不超过 W。历史配额是分层触发依据，最终完整请求校验是硬边界。

关键配置合同：

| 配置 | 默认/含义 |
| --- | --- |
| `MODEL_CONTEXT_WINDOW` | 128000，应用使用的模型窗口；换模型时配置真实可用值 |
| `MAX_HISTORY_TURNS` | 32，预算目标轮数，不直接对完整历史做 `[-32:]` |
| `MAX_OUTPUT_TOKENS` | 2000，最终输出上限 |
| `MAX_USER_INPUT_TOKENS` | 2000，当前用户输入上限，超过时不调用模型 |
| `MAX_AGENT_STEPS` | 4，最多执行工具步数；允许最后一次收敛决策 |
| `TOOL_RESULT_MAX_TOKENS` | 1200，应用接纳/回灌的工具结果限额 |
| `RERANK_TOP_K` | 10，允许 1～10；演示设为 5，检索及证据选择必须实际遵守 |
| `TOKEN_SAFETY_MARGIN` | 512，和估算器一起验证，不能单独改小掩盖低估 |

固定开销的预留项和稳态估算由显式预算配置/校准产物提供，日志展示其来源；不得隐藏一笔用于凑结果的常量。证据选择仍保留完整 chunk，数量/总量超预算时减少整块，不切掉关键限制条款来塞满 Top-K。

兼容 `CONTEXT_WINDOW_TOKENS` 旧名称；新旧同时设置但不同值时启动报清楚的配置冲突，不静默忽略用户配置。`MAX_AGENT_STEPS` 与旧步数配置采用同样的明确映射/冲突校验。升级文档必须提醒旧 `.env` 的 8192 会覆盖默认值；不改动密钥。演示脚本显式构造两个配置组，避免污染常用服务。

启动打印全部预算扣除项，并用稳态一轮和最大本轮峰值自检；连一轮正常历史也容纳不了时，以“上下文预算不足”明确阻止错误配置上线，而不是启动后反复丢空滑窗。

原有“每轮累计模型消耗上限”继续独立存在。默认额度按可达调用次数与各阶段预算推导，不能沿用旧的 49152 导致长历史首次进入 ReAct 就耗尽。用户显式设置更小限额时说明限制并遵守它；实际计费仍以供应商 usage 为准。后台摘要另设任务预算，不向已完成聊天轮次补记消耗。

## 11. 摘要等待、失败与超长会话

摘要运行时，尚未被已完成摘要覆盖的层 2 仍可用于当轮输入；不能仅因任务已开始就跳过它或提前推进摘要锚点。层 2 超配额意味着应调度摘要，不等于立即删除这批内容。

如摘要积压且完整请求已经达到实际窗口硬上限，先执行合法的整轮分层调整并重新核对；仍装不下时立即返回明确的上下文预算/整理中兜底，不等待摘要模型、不发送超长请求，也不偷偷删除用户原话。该路径要有独立日志原因。正常默认/演示 24 轮验收不得靠这种兜底过关。

所有完成摘要按顺序保留并默认注入，不通过“只取最后几段”悄悄丢失最早订单。极长会话中，摘要本身最终也可能超出有限窗口：本章明确拒绝该次超限请求并提示新建会话，不做递归摘要、语义挑选、跨会话迁移或无限上下文承诺。

## 12. 持久化、故障恢复和迁移

MySQL 与 PostgreSQL 不是分布式事务。本章继承“先持久化确认再发 done”的边界，并按版本设计恢复：

- v1 旧会话先核验旧 checkpoint 与 MySQL 交集的一致性，再用 MySQL 中完整合法轮次补齐此前被裁掉的历史；新建稳定消息 ID，升级为 v2。无工具的旧消息也能回载。迁移不调用业务工具或付费模型。
- v2 的用户/客服原文和有限工具元数据与 MySQL 核对；完整工具结果和配对以 checkpoint 为准。MySQL 最终轮次元数据保存规范化完整轮次的指纹，恢复时核验，不依赖 MySQL 中不存在的工具正文。
- MySQL 已确认完成、最终 checkpoint 确认丢失时，只有已持久的节点结果/前置状态和原文/指纹可完整验证时才修复；不得重新执行工具或重新生成已经显示的答复。
- checkpoint 缺失且 MySQL 已采用 v2 不保存工具结果时，不能伪造 ToolMessage 恢复完整历史；报明确恢复冲突，保留原文回载能力。
- 中断轮次结算为 failed/cancelled，保留已显示文字，不进入正常模型历史。幂等恢复不重复消息、工单、摘要或业务调用。
- 已完成摘要与锚点通过 MySQL 事务一致读取；后台处理旧快照时只提交已冻结的连续前缀，版本/租约冲突按 skip 或重新检查处理。

提供显式、幂等的 schema 迁移和 check-only 检查。应用启动检查结构，不私自执行破坏性迁移。实现前备份并使用隔离 MySQL/PostgreSQL 验证新旧混合数据；不删除旧 tool 行，不批量重写原文。

## 13. 两个只读接口

继续由服务端确定当前用户（本章为既有 demo 用户），不接受前端传任意 user_id 来读取其他人的会话。两个 GET 接口不触发恢复写入、模型调用、摘要生成或工单动作。

`GET /api/conversations`：按 `created_at DESC, id DESC` 返回当前用户所有会话，采用游标分页（默认 50、上限 100）。前端可逐页加载全量，不能只展示第一页就称为全部。每项包括 ID、状态、创建/活动时间、首问预览、已摘要标志、摘要段数及是否正在整理。预览最多 60 个 Unicode 字符，显示时作为文本。

`GET /api/conversations/{id}/messages`：检查归属，不存在/非本用户统一 404。按 ID 升序分页（默认 100、上限 200），返回用户和对客客服原文、轮次 ID/状态、时间及恢复展示需要的工具徽章、引用快照和操作状态。返回原文，不返回模型用的截短副本或摘要来冒充历史。包括失败/取消轮次的已保存文字及明确状态。

接口不返回内部推理、完整工具正文、checkpoint 内容或运行凭据。历史引用用当轮已保存的来源快照；工单按钮根据原有 action 的真实状态恢复，读取历史不得重新创建工单。

## 14. 页面行为

现有侧栏增加会话列表：新会话在前、首问预览、当前项高亮、已摘要标记。点击后逐页回载完整原文；工具徽章、引用弹窗、反馈锁定和工单状态继续可用。

“新对话”清空当前视图并进入新会话草稿，第一条消息仍通过现有聊天 POST 创建会话；不用 GET 来建空壳。旧会话保留在侧栏。刷新可恢复上次选中的会话 ID；本地存储不可用时仍能通过侧栏选择。

流式回复期间暂时禁用会话切换/新建，用户先停止回复再切换；防止旧 SSE 片段写入新会话气泡。切换加载使用请求取消或代次标识，晚到结果不能覆盖新选择。切换后的下一条消息使用对应 session_id，不把其他会话历史拼进去。

会话列表加载失败静默降级，保留聊天和“新对话”能力；历史回载失败保持原视图并给出局部重试，不把空白假装成该会话原文。手机端提供会话入口，不因原侧栏隐藏而失去切换能力。

## 15. 可观测与日志

本地文件 `log/app.log` 使用可 grep 的事件名和完整 JSON 字段，配置轮转；`log/` 全部排除 Git。按用户要求记录模型收到的会话内容原文，但不记录 API Key、连接 URL 密码、认证头或供应商隐藏思考。

- 每轮一次 `history_ctx`：conversation_id、turn_id、摘要全文/段号、逐条历史视图、层级、窗口条数、tokens 估算、两个锚点和预算扣除项。闲聊、投诉、兜底和未进入 Agent 的轮次也有。
- 每次 Agent 决策/最终生成之前 `model_ctx`：阶段、调用序号、实际 message 顺序/role/内容/tool_calls/tool_call_id、完整摘要/证据背景、工具 Schema、窗口条数、估算 token 和输出余量；日志必须来自即将传入网关的同一对象，不能重新拼一份“近似日志”。
- 其他模型调用也记录实际上下文并标明 stage；校验拒绝请求时标明 `request_sent=false`，不能把未发送输入称为实际已发上下文。
- `layer1 demote`：旧/新锚点、降级轮次、降级前后用量与配额，对应人可读信息“层1 降级 X→Y”。
- `summary trigger/start/done/skip/fail`：会话/任务/段号、冻结覆盖区间、实际完成区间、触发用量与配额、耗时、尝试次数及安全原因；no_facts、任务已有、队列满、陈旧租约都明确区分。

摘要开始/完成时间与 SSE 首 token/done 时间可对照；非阻塞性另用可控阻塞测试证明，不能仅凭两条时间相近的日志断言。

## 16. 验证与验收

### 16.1 后端 TDD

覆盖预算逐项算式、中文/JSON/Unicode 计量、配置别名冲突、工具峰值累积、按用量触发、整轮边界、短/长工具结果、原文不可变和 reducer 幂等。覆盖后台重复触发、超时/格式失败、租约过期、队列满、任务期间新轮次、事务失败、no_facts、shutdown/restart 和不会改写活跃 checkpoint。

真实隔离 MySQL/PostgreSQL 集成验证：两个锚点与新表约束、停止写完整工具结果、v1→v2 迁移、v2 恢复/指纹冲突、确认丢失不重放工具、两个 GET 的分页/归属/只读性。已有 Workflow、检索证据闸、工具、工单、SSE 和 GitHub 同步测试必须继续通过。

### 16.2 Prompt 与 token 校准

标注集包含多型号、多订单、显式手机号、否定、更正、未决问题、纯闲聊、模型诱导编造和超长工具。报告原样列出期待事实、实际摘要、缺失/多出事实、标识匹配、来源验证、长度及真实 usage。

校准样例覆盖无工具、有工具 Schema、多个工具结果和摘要+证据背景。统一调整估算器与预算配置；日志同时记录估算与实际值。新供应商需要重新验证，不能把 DeepSeek 的比例宣称适用于所有模型。

### 16.3 两组 24+ 轮演示

两组使用同一套至少 24 轮、有标注的演示对话，不通过降低层预算、直接改锚点或伪造摘要来制造结果。首轮明确给出订单号及待解决诉求，后续包含足量业务内容和真实工具轨迹，最后问“最开始那个订单后来怎么说”。

| 配置组 | 验收结果 |
| --- | --- |
| 默认窗口 128000、目标 32 轮 | 24 轮样例无任何层 1 降级、无摘要触发；完整历史可继续回答；不是对任意无界输入保证永不压缩 |
| 演示窗口 18000、输出 2000、输入 2000、步数 3、工具结果 1200、Rerank Top-K 5 | 日志出现层 1 降级 → 层 2 用量超预算 → 后台触发/开始 → 新摘要段完成；最后能从梗概取出原订单号与诉求，必要时据此查当前工具 |

两组均检查每次输入估算 + 输出预留 + 安全余量不超窗口，且没有因预算/恢复错误走固定异常兜底。演示预算日志报告真实 H/L1/L2 和每笔扣除，不断言原示例的三个数字。

确定性测试使用阻塞栅栏让摘要模型持续等待，同时断言当前聊天仍发出 token/done；释放后才出现 summary done。真实 DeepSeek 演示另报耗时/usage 与语义结果，不把脚本模型测试说成真实模型验收。业务工具继续明确为演示数据，不能拿随机状态差异判模型记忆错误；验收重点是订单标识和诉求正确、有依据。

浏览器验收开至少两个会话，来回切换、刷新、回载全部原文、继续聊天，确认不串会话；另测列表请求失败、回载竞态、移动端、引用/工单/反馈回归。
