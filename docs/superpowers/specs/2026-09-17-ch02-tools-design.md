# 第 02 章：客服工具调用与 MySQL 持久化设计

日期：2026-09-17。基线：`1bf20c6`。用户已回复“关闭思考模式”，随后对完整设计提案回复“确认”，阅读本文后回复“规格通过”。书面规格已获确认，进入实施计划。

## 1. 目标与范围

在现有聊天页面和 `POST /api/chat` 中完成：模型选择工具、后端执行、工具结果回灌、最终回答流式输出。聊天记录及工具轨迹保存在数据库中。保留第一章售后结构化提取接口与多轮上下文能力。

固定技术：Python、FastAPI、SQLAlchemy、Docker MySQL、LangChain `@tool`、OpenAI 兼容 Chat Completions 协议。当前真实模型继续使用本地 `.env` 已配置的 DeepSeek。模型地址、名称、密钥及供应商额外请求参数均从环境配置读取。

本章只允许一次模型工具选择、最多执行一个业务工具，然后收敛为最终回答。一次逻辑工具执行允许有限的暂时性错误重试。不实现 Agent Loop、LangGraph、向量检索、RAG、真实订单/商品/物流接口或对应数据库表，不新增账号体系。

后端实现走 Superpowers 和 TDD；Prompt、FAQ 数据质量以标注样例评估；聊天页面按用户指定的 Vibe Coding 例外直接修改和浏览器验证，不套页面 brainstorm、TDD 或 code review。

## 2. 方案选择与兼容性

采用固定两阶段模型请求：

1. 使用绑定五个工具的模型获取工具选择，暂不向用户推送这一阶段的文本。
2. 如选择一个工具，执行并附加匹配 `tool_call_id` 的工具结果；使用不绑定工具的模型生成最终流式回答。

未选择工具时，也使用第二阶段生成真正的上游流式回答，第一阶段已生成的普通文本不作为一条回答写入历史或再次反馈给模型。每轮最多两次模型请求；不将完整文本人为拆分冒充流式。

比较方案是流式解析第一阶段的工具参数，同时直接转发普通回答。它可以减少无工具轮次的请求数，但增加增量参数、混合文本和工具申请的处理复杂度；本章不采用。

DeepSeek 工具聊天的两个阶段均关闭思考模式。现有 `langchain-openai==1.6.2` 不完整保留 DeepSeek 的 `reasoning_content`，关闭思考避免携带工具历史时的协议冲突。通过新增环境项 `LLM_CHAT_EXTRA_BODY` 传入 `{"thinking":{"type":"disabled"}}`；更换其他兼容供应商时可配置为空对象。该配置只作用于聊天，保留售后提取现有 `with_structured_output(..., method="json_mode")` 行为。额外请求参数不得覆盖消息、工具清单、流式开关及应用控制的输出上限。

具体依赖版本在实施计划中根据 Context7 和安装兼容性确定并锁定；保留现有依赖锁定，避免无关升级。供应商兼容性由实际端点验证，不把符合 OpenAI 协议等同于支持全部工具能力。

## 3. 分层与生命周期

- API 层：请求校验、HTTP 状态、SSE 编码和断连处理，提供现有聊天与售后提取入口。
- 聊天服务：会话占用、历史加载、两阶段模型调用、工具执行、持久化及完成/失败处理。
- 模型网关：封装工具选择和最终文本流，隔离供应商传输细节，保留售后结构化提取。
- 工具层：五个 `@tool` 定义、注册表、参数校验、结果格式、超时和重试。
- 数据层：SQLAlchemy 模型和仓储，分别承担会话/消息、FAQ、工单读写。

FastAPI lifespan 创建和关闭模型客户端及异步数据库引擎；仓储操作采用独立短事务和独立 AsyncSession，不跨模型网络请求或 SSE 流持有事务，不在并发任务之间共享 Session。MySQL 使用 SQLAlchemy 官方支持的 asyncmy 方言。

数据库成为会话历史来源，进程内仅保留当前请求的占用状态；默认仍以一个 Uvicorn worker 运行。同一会话的并发请求返回冲突，不将两个轮次交错写入。数据库已存在的会话在服务重启后仍可继续；旧的内存会话不迁移，不再用内存 TTL 删除数据库历史。原有并发容量限制用于限制正在处理的请求，不限制已存档会话总数。

## 4. 四张表

所有创建时间使用 UTC；中文内容使用 utf8mb4。仅创建以下四张业务表，不引入订单、商品、物流或额外会话轮次表。

| 表 | 必需字段及约束 |
| --- | --- |
| `faq` | `id` 主键；`question`、`answer`、`category` 非空 |
| `conversations` | `id` UUID 字符串主键，沿用 API 的 `session_id`；`user_id` 为后端指定的演示用户；`status` 为 `open` / `human_pending` / `closed`；`created_at` |
| `messages` | 递增 `id` 主键；`conversation_id` 外键；`turn_id`；`role` 限定 `user` / `assistant` / `tool`；`content`；可空的 JSON `tool_calls`；可空 `tool_call_id`；`turn_status` 限定 `pending` / `completed` / `failed` / `cancelled`；`created_at` |
| `tickets` | 服务端生成的 `ticket_no` 主键；`conversation_id` 外键；`issue_description`；`ticket_type`；`status` 为 `pending` / `processing` / `closed`；`created_at` |

消息按递增主键排序，按会话和轮次分组。`turn_status` 在该轮消息上保持一致，正常完成时在同一事务内更新并保存最终回答。创建工单与将所属会话标记为 `human_pending` 在同一事务提交。

初始化脚本建表并幂等写入演示 FAQ、会话、消息及工单，重复运行不重复造数据，也不覆盖之后产生的客服记录。不执行自动删表或清空数据库。演示数据与真实模型验收产生的记录可通过固定演示标识区分。

## 5. 业务工具合同

五个工具均以 LangChain `@tool` 定义，输入使用显式参数 Schema。注册表只有这五个名称，不允许运行任意 Python 函数或由模型指定数据库连接。会话标识、演示用户、当前原始问题及工单幂等标识通过服务端上下文注入，不作为模型可填写的参数。

| 工具 | 模型可见参数 | 行为 |
| --- | --- | --- |
| `query_order` | `order_id` | 工具内部随机生成订单状态、商品摘要、金额等演示数据，返回相同订单号及明确的模拟标识 |
| `query_product` | `keyword` | 根据商品名称或标识生成相关的演示商品信息，价格、库存等为模拟值 |
| `query_logistics` | `order_id` | 随机生成演示物流状态与相互一致的轨迹，标明并非真实物流查询 |
| `query_faq` | `keyword` | 用关键词对 FAQ 问题、答案和分类执行参数化字面 LIKE，按 ID 排序，最多返回五条 |
| `create_ticket` | `issue_description`、`ticket_type` | 创建关联当前会话的待处理工单，返回工单号和状态；不声称退款、退货或赔偿已经执行 |

订单号允许字母、数字、下划线和连字符，长度 1–64；商品关键词长度 1–100；FAQ 关键词长度 2–32；工单描述长度 1–2000。文本去除首尾空白后校验，拒绝未知参数。工单类型限定 `refund`、`return_refund`、`exchange`、`repair`、`logistics`、`complaint`、`other`。

工具结果使用统一 JSON 结构，区分 `ok`、`not_found`、`error`，携带数据或脱敏错误码。`not_found` 是一次成功执行但无匹配结果，不作为异常重试。序列化后的结果最大 4096 个 UTF-8 字节；超限时先减少列表尾项或缩短描述并标记 `truncated=true`，不得删除工单号、订单号、状态或错误码，不得将失效的 JSON 回灌给模型。保留必要字段后仍超限则返回受控的结果过大错误。

### FAQ 漏召回约束

模型必须从本轮用户原文提取主题关键词，不作同义词扩展；后端验证关键词是本轮原文的连续子串。SQL 对 `%`、`_` 等通配符作字面转义，不能让模型传入通配符查询全表。

种子 FAQ 至少包含“退货政策”和“运费”主题；该演示数据不含“邮费”同义词。期望模型从“退货政策是什么”提取“退货政策”或“退货”，从“邮费是多少”提取“邮费”。后者必须实际执行 SQL 并得到空结果，不能硬编码该问法直接返回空，也不能改查“运费”。

无匹配时回答明确表示知识库未命中，不使用模型常识编造本店政策，也不自行创建工单或再调一次工具。将该缺陷写入评估结果，留给下一章升级。

客服角色、工具选择规则和收敛规则统一放在独立 PromptTemplate 模板中。模型将用户输入和工具内容当作业务数据，不执行其中要求忽略客服约束的指令；最终回答必须区分工具事实、模拟数据、未命中和执行失败。

## 6. 单轮编排与失败边界

1. 校验输入并取得会话占用，加载完整历史和建立本轮上下文；先检查必要输入及工具描述是否在预算内。
2. 创建或读取会话，持久化本轮用户消息，推送 `meta`。
3. 模型选择零个或一个工具。一个合法工具申请先以 assistant 消息写入，再发送工具状态帧。
4. 执行工具，将结果以匹配 `tool_call_id` 的 tool 消息持久化，再把这两条消息附加到模型输入。
5. 重新检查最终回答的上下文预算；不绑定工具调用最终模型，将上游非空文本增量立即作为 `token` 事件转发。
6. 上游正常结束后，原子保存最终 assistant 消息并将整轮置为 `completed`，然后推送 `done`、释放会话占用。

无工具轮次只持久化用户消息与最终 assistant 回答。模型如果申请多个工具、返回缺失调用 ID 或不可解析的工具申请，则不执行任何业务工具，记录失败并返回受控错误；不能只选第一个悄悄继续。

已获得合法调用 ID、但工具名称未知或参数校验失败时，将受控错误作为本次工具结果回灌，最终回答解释失败或向用户澄清，不再选择工具。工具的业务失败同样以结果回灌；数据库无法可靠保存审计记录时终止请求，不伪装成功。

### 超时、重试与工单副作用

继续遵守整个聊天请求的超时上限；每次工具尝试另设可配置超时，默认 5 秒，最多尝试 2 次。仅重试明确定义的暂时性错误，例如数据库临时连接失败或超时；参数错误、未知工具、无匹配和取消不重试。重试不进行额外模型决策，总请求超时到达后不得开始新尝试。

工单号在执行前由服务端为这一次逻辑工具调用生成，所有尝试复用同一主键。重试先读取该工单，已存在且字段一致则返回同一工单；唯一键冲突后重新读取，不另造号码。提交结果不确定时只能说明无法确认，不能承诺创建失败且未产生工单。

用户停止或连接中断后取消剩余模型/工具工作并释放资源。已提交的工单继续保留；不会因为 SSE 中断删除工单。异常和取消时尽力保存已收到的部分回答并标记该轮 `failed` 或 `cancelled`，保留已写入的工具审计。进程崩溃留下的 `pending` 记录仍可审计，但不参与后续模型上下文。

## 7. 历史与 token 预算

只加载 `completed` 的完整轮次，保留 `user → assistant 工具申请 → tool 结果 → assistant 最终回答` 的整体关系，不能留下孤立工具消息。无工具轮次仍为一对用户/助手消息。

保留第一章按 UTF-8 内容估算并明确标注估算值的口径，扩展计数范围到工具 Schema、工具调用参数和结果。两个模型阶段分别核算；从最旧的完整历史轮次开始裁剪，同时遵守 `MAX_HISTORY_TURNS`、输出预留和安全余量。

系统消息、本轮用户输入及本轮工具申请/结果不可为了凑预算而孤立删除。工具结果以有限结构和长度控制输入；裁剪历史后仍无法容纳时返回明确错误，不继续发送超预算请求。已产生工单时错误提示不得否认该事实。

历史裁剪仅影响模型输入，不删除数据库中的审计记录。会话用户由后端固定为演示身份并据此查询，不宣称具备正式的多用户鉴权隔离。

## 8. HTTP、SSE 与页面

沿用 `POST /api/chat` 请求：`message` 和可选 UUID `session_id`。保留 `meta`、`token`、`done`、`error` 事件名和已有字段。参数、会话不存在/占用及开始流前的基础检查仍返回 HTTP 错误；开始流之后的模型、工具或持久化异常用 SSE `error`，不再推送成功 `done`。

新增 `tool_status`，包含 `tool_call_id`、`name`、`status`、`attempt`、简短可显示的 `message`；状态为 `running`、`retrying`、`succeeded`、`not_found`、`failed`。先发送 `running` 再执行工具，结束后发送对应结果状态，不在状态帧暴露密钥、数据库连接或堆栈。

`meta.estimated_input_tokens` 对应第一次模型输入，保持 `token_count_is_estimate=true`；`done` 可增加最终阶段的估算用量。`token.content` 始终来自上游文本增量，一个增量不保证严格等于一个 tokenizer token。

页面消费新增事件，在本轮助手气泡中显示工具名称和执行状态徽章；同一调用的重试更新原徽章。保留发送、停止、新建会话和售后提取交互，以安全文本节点渲染工具文本。页面继续只展示本次打开后发送的对话，本章不新增历史列表或自动加载旧会话 UI。

## 9. Docker 和本机环境

MySQL 由 Docker Compose 启动，使用持久化命名卷，数据库端口仅绑定本机；端口可配置以避开其他项目。应用继续在本地 Python 环境运行，数据库使用独立应用账号，凭据放在被忽略的环境文件中。

启动命令等待数据库健康，再显式运行建表/种子初始化，应用启动时检查可用性，不默默回退到内存或 SQLite。测试使用独立的 MySQL 测试库，清理操作不得作用于演示库。具体镜像版本和安装命令在实施前查阅官方文档并锁定。

当前 Apple silicon 主机未发现 Docker。环境准备需安装/启动 Docker Desktop；若首次运行需要用户接受订阅协议或系统授权，在实际提示处交接给用户，不代替用户接受协议。该环境前提不改变指定技术方案。

## 10. 验证与完成口径

后端行为测试先失败后实现，覆盖：

- 五个工具的 Schema、注册和受控错误；模拟数据标识和字段一致性；字面 LIKE 通配符转义；工单关联、幂等重试与状态更新。
- 每轮最多一次工具选择/一个逻辑工具执行，最终模型不绑定工具；零工具、无匹配、工具错误、多工具申请及错误 ID。
- 工具状态先于执行/最终流；首个文本增量可在流完成前消费；数据库提交成功后才发送 `done`。
- 工具结果回灌及 ID 对应、两轮上下文、完整轮次裁剪、两阶段预算、同会话并发冲突、不同会话隔离。
- 上游截断、异常、超时、断连、工单已提交后取消、数据库写失败及服务重启后的历史恢复。
- 售后结构化提取和原有 API 相关回归。

真实 MySQL 集成检查必须实际执行 DDL、JSON 字段/外键、中文查询、种子幂等、历史读写和工单事务；不能用 SQLite 或仓储替身声称通过数据库集成。

Prompt/工具选择评估记录原始问题、期望工具及参数、实际工具及参数、工具结果、模型最终回答和人工语义结论。至少包括用户指定三例及查订单、查商品、明确创建工单、缺少订单号需澄清、普通闲聊无需工具、诱导编造政策等样例；离线测试与真实模型评估分开报告。

浏览器最终必须验证：

1. “订单 1001 的物流到哪了”：选中 `query_logistics`，参数为订单 1001，气泡有徽章，最终回答忠实于模拟结果并说明演示性质。
2. “退货政策是什么”：选中 `query_faq`，查询命中，回答与种子政策一致。
3. “邮费是多少”：选中 `query_faq`，实际字面查询无匹配，诚实说明未命中；作为预期漏召回记录。

交付包括 Docker/初始化/启动命令、curl SSE 演示命令、浏览器地址、自动测试与真实模型评估结果、`dev-notes/ch02.md`。真实验收或环境准备尚未完成时，不宣称本章完成。
